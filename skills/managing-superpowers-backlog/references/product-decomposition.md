# Product decomposition and native intake

Use for `decompose/intake`, obligation/coverage assessment, and Project
reconciliation. Policy lives in [governance](../../../docs/superpowers-backplane/governance.md).
Read the [native issue contract](github-issue-contract.md) and
[Superpowers binding](superpowers-binding.md). GitHub authority and mutation
rules remain unchanged. This operation consumes approved intent; it is not a
new general interviewer or an alternative development lifecycle.

## Inputs and assessed output

Require the approved product/design locator, immutable or consumed semantic
revision, criterion/obligation wording and keys, approval evidence, code legend,
owners, proposed contributions, and declared presentation mode. Missing input
is an explicit unresolved question. For every existing candidate, obtain all
15 native issue intake fields before interpreting its body or relationships;
read supplied complete fixture records in a read-only probe instead of live gh.

Return an assessment with these parts:

1. **Authority:** approved inputs/revisions, approval scope, actual operation
   authority, mode, and missing/changed inputs.
2. **Obligation accounting:** one row per parent obligation, including governing
   revision, owner, bounded contributions, existing evidence, and disposition.
3. **Issue reconciliation:** existing match with retained issue identity;
   proposed new bounded outcome; or unresolved mapping/scope/ownership question.
4. **Native graph proposal:** actual observed parent/dependency/type/PR facts
   and separately proposed relationship changes. Never infer edges from codes.
5. **Coverage/evidence:** explicit many-to-many criterion/requirement and PR
   contributions, exact accepted evaluation inputs, current applicability, and
   UNKNOWN/UNSATISFIED/SATISFIED conclusions with limitations.
6. **Permissible next operations:** distinguish read-only refinement, authorized
   intake, per-issue planning, readiness, explicit selection, and execution.
   A proposal alone authorizes none of the latter mutations.

## Adequacy and issue-owned records

For each approved parent obligation require a bounded child contribution,
eligible accepted evidence, or an explicitly approved exclusion/deferral.
Omissions remain unresolved. Reject unrelated scope and ambiguous overlapping
full ownership. Shared coverage is valid with specific contribution boundaries
and the owner accepting the combined result. Deferral/exclusion is an approved
scope disposition and never a satisfaction result. Preserve failed/unavailable
historical evidence and changed requirements rather than retargeting their pass.

A participating issue uses the following body sections. They supplement its
existing executable leaf contract and are canonical on the issue:

```markdown
## Backplane Record

Code: <project-owned unique code>
Kind: capability | outcome | gate | external-boundary
Namespace and governing design/plan/approval references: <identities/revisions>

## Obligation Dispositions

| Obligation and governing revision | Owner | Child contributions or existing evidence | Disposition and approval |
| --- | --- | --- | --- |

## Coverage and Satisfaction

| Criterion and wording/revision | Requirement keys/revisions | Contributions | Latest accepted evaluation and applicability | Current result and gaps |
| --- | --- | --- | --- | --- |
```

These are input slots, not invented approvals. Fill from observed approved
sources. Omit an inapplicable parent table with an explicit not-applicable note;
retain every applicable obligation. Actual parent and dependency edges stay
native; the tables reference them without introducing a separately editable graph.
Code/kind identity survives milestone retargeting and Project removal. A proposed
child is not a native child, delivered result, eligible issue, or selected work.
An existing matching issue remains the same work item.

Current criterion-to-requirement mappings and evaluation pointers belong in the
outcome issue. Accepted evaluation records are immutable project-owned evidence,
identifying criteria/revisions, implementation/integration commit, method/result,
review/acceptance, evidence identities and availability, and outstanding work.
A mutable issue claim or Project mirror is not the accepted evaluation itself.
Parent summaries reference those results. Keep historical evaluations intact.

Compare evidence against current approved requirements and relevant delivery
inputs. A behavior-changing S2/C invalidates reuse of S1/B for affected criteria
until reconciled/revalidated; classify unsupported claims UNKNOWN rather than
SATISFIED. A known failed applicable check is UNSATISFIED. Editorial S2e may
retain matching evidence only with the supplied semantic-equivalence approval
and matching implementation; it cannot repair a different historical gap.

## Intake, planning, and selection

Before an authorized write, re-read issue bodies/native relationships and
reconcile drift against the approved decomposition. Present exact body/graph
changes, owners, uncovered scope, and approval conflicts. Apply only the
selected authorized changes through gh, preserve unrelated fields/labels, and
re-fetch to verify the actual native graph. Never create a duplicate because
an issue is missing from a Project. Unknown provenance or authority stops the
corresponding write rather than silently widening scope.

Product planning precedes decomposition/intake reconciliation; each resulting
bounded leaf then gets one current approved issue-bound implementation plan.
An already captured bounded approved issue may start directly from its own
issue-body design authority. Cross-cutting work uses its approved specification.
Do not repeat already settled design. Record issue/design consumed revisions,
acceptance/verification seams and exact project checks in the plan. Check all
ready/leaf/blocker gates before execution selection. Neither approved design,
a drafted plan, intake publication, nor a recommended item implies readiness
or priority. Existing lifecycle transitions require their own evidence.

## Projects and compatibility mode

Declare `integrated` or explicitly selected `issues-only` mode. The default
proposal for new governance presentation is integrated Projects; legacy native
status/selection remains operational without Project state. Project-only drafts
may capture ideas but do not replace approved issue records.

| View | Sources and useful grouping |
| --- | --- |
| Product/decomposition | Code, kind, native parent/children, explicit obligation dispositions and owners |
| Execution | Native labels/state, issue type if available, assignees, dependencies, linked PR context |
| Satisfaction | Current criterion/evaluation pointers and accepted results, stale/missing evidence and unresolved obligations |
| Release targets | Native milestones and PR contributions, separately recorded release authority |

Use native Title, type, labels, assignees, parent/sub-issue progress, milestones,
and PR context. Optional Code/Kind/Satisfaction fields mirror the issue-owned
records and accepted evidence; record source and refresh responsibility.
Optional Status maps explicitly to issue lifecycle/native state and does not
decide eligibility. No custom organization type is required when native types
are unavailable.

Reconcile a mismatched Code from the canonical issue code; Done cannot override
review or UNKNOWN integrated verification. Closed-child progress is not parent
satisfaction, and not-planned closure supplies no delivery of the obligation.
Propose repairs under authority, without performing them in a read-only request.
Denied integrated-mode Project capture is incomplete: keep that declared mode
and permission limitation. Do not infer fields or silently select issues-only.
An explicitly selected issues-only capture preserves the same obligation,
coverage, evidence, and lifecycle contract without claiming Project coverage.

After authorized material intake/scope/coverage reconciliation, request the
checkpoint operation under its own applicable authority. A Project mirror
refresh or checkpoint does not become the sole current mapping source.
