# Backplane v0.1 Adoption, Installation, and Mutation Contract

- **Status:** Conversational design approved; written specification awaiting review
- **Work item:** https://github.com/tvproductions/superpowers-backplane/issues/2
- **Issue revision reviewed:** `2026-09-19T13:06:19Z`
- **Supersedes:** The bootstrap design's generic skill-link installation surface where this document defines a native plugin surface.

## Purpose and scope

Backplane v0.1 makes the existing backlog and handoff skills adoptable in Codex,
Claude Code, and OpenCode while preserving upstream Superpowers as a separate
dependency. A successful adoption lets a user discover both Backplane skills and
the installed upstream `using-superpowers` skill in a fresh session, then use
native GitHub Issues for product continuity without an additional runtime in
the consuming project.

This specification governs packaging, dependency setup, installation lifecycle,
and issue-state mutation. Issue #2 produces this contract and its implementation
plan; implementation of the three installation surfaces belongs to executable
follow-up issues. No other harness is part of v0.1. GitHub Projects, IssueOps, a
Backplane daemon, and a required Python or Node.js runtime are outside scope.

## Authorities and dependencies

- The consuming project's rules govern its build, tests, branch policy, and
  permissions. Backplane does not impose a project runtime or test runner.
- The GitHub issue and its native hierarchy, blockers, labels, linked pull
  requests, and closure reason govern backlog state. A local specification
  governs approved design; a current Superpowers plan governs execution.
- Git and authenticated GitHub CLI (`gh`) are required. Compatibility is checked
  by required `gh` capabilities, not by a fixed version string.
- The selected harness and upstream Superpowers must be operational. Upstream
  retains its own installation identity, version, update path, and uninstall
  path. Backplane never vendors or copies upstream files.
- The default upstream channel is the latest compatible stable release. The
  upstream default branch is an explicit edge-channel choice. An upstream
  update is separately authorized and preflighted under `SUPERPOWERS.md`.

## Package architecture

One versioned Backplane source tree owns the canonical root `skills/` directory.
Its `managing-superpowers-backlog` and `managing-superpowers-handoffs` skill
folders and their references are the only authored copies. Harness metadata and
the OpenCode adapter point at these folders; they do not duplicate skill text or
upstream Superpowers content. All package identifiers use the stable name
`superpowers-backplane` where the host permits it. A release uses the same
Backplane version in every manifest and marketplace entry, and its Git tag
resolves one immutable source revision. Update and rollback instructions name
that revision; an unpinned moving branch is not the default install source.

| Target | Native package surface | Skill discovery |
|---|---|---|
| Codex | Root `plugin.json` and a repository marketplace entry under `.agents/plugins/marketplace.json` | The plugin declares the root `skills/` tree. |
| Claude Code | `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` | Claude Code loads the root `skills/` tree in the plugin namespace. |
| OpenCode V1 and V2 | Root package metadata with one JavaScript plugin entry point | The entry point registers the root `skills/` tree with each host's native plugin API. |

OpenCode's adapter supports the V1 and V2 plugin contracts from one package
entry point. V1 uses its `plugin` package configuration and V2 uses `plugins`.
The minimum supported releases are V1 1.18.29 and V2 2.0.4; older host
releases require a separate compatibility decision. The adapter registers the
canonical Backplane skills through each host API. Upstream Superpowers owns
session bootstrap; Backplane does not inject a competing bootstrap. The adapter
carries no separate backlog rules or dependency manager. The JavaScript
runtime that loads this adapter belongs to OpenCode, not the consuming
project.

Codex, Claude Code, and both OpenCode variants install Backplane through their
documented native plugin mechanisms. A local source may be used for development;
release instructions identify a versioned Git source. Each host's installed
Backplane package is managed by that host. No repository-local control file in
a consuming project silently becomes a second Backplane installation.

## Adoption and setup

After adding the Backplane plugin, the installation instructions invoke a
Backplane setup workflow in the active harness. The plugin package does not
execute setup on its own, and package installation alone does not assert that
Backplane is ready. The README and harness installation instructions direct
the user to request Backplane setup in that harness. The agent follows
`skills/managing-superpowers-backlog/references/installing-superpowers.md`
to establish upstream before any backlog operation. The workflow performs
these checks in order and reports the observed result:

1. Identify the active harness and supported plugin API. Confirm exactly one
   effective Backplane installation and that both canonical skills are visible.
   A duplicate or conflicting install is reported for reconciliation.
2. Find the harness's operational upstream Superpowers installation. If one
   exists, verify its authoritative source and required skills, then adopt it
   without relocating or editing it. A compatible sibling Git checkout remains
   valid where the harness or development workflow uses one.
3. If upstream is absent, obtain it through that harness's documented native
   installation channel, selecting the current stable upstream release by
   default. Where a checkout is necessary, create a separate Git checkout with
   the authoritative `obra/superpowers` origin. Preserve host confirmations and
   permissions. Never silently modify an existing upstream installation.
4. Check `gh auth status`, the complete native issue intake fields, label
   addition/removal, and closure-reason support. A failed capability check is
   an incompatibility even if a displayed CLI version looks sufficient.
5. Start a fresh session and confirm discovery of upstream
   `using-superpowers`, `managing-superpowers-backlog`, and
   `managing-superpowers-handoffs`. Only then report adoption complete.

A native upstream package may not leave a physical Git checkout. For that
case, verify the harness's package source identifies `obra/superpowers`, record
the resolved tag or commit and installed package version, and confirm the
required skills in a fresh session. For a sibling or managed checkout, verify
its canonical path, authoritative Git origin, revision, and clean state before
an update. Unknown package provenance fails closed. The implementation must
extend `installing-superpowers.md` to recognize native package provenance;
its existing checkout rules remain valid for checkout mode.

The setup workflow may explain or repair a partial Backplane-owned install, but
it does not overwrite user files, a dirty Git checkout, or another package's
configuration. On failure, it names the failed check and a recovery action,
leaves existing user work intact, and does not change any GitHub issue state.

## Update, rollback, and uninstall

Backplane and Superpowers have independent lifecycles. Before changing either,
record its current source and resolved version, inspect the candidate, and run
the relevant compatibility preflight. Stable versions are the default; a
moving upstream branch is never an implicit update target.

- **Backplane update:** Use the active harness's native plugin update mechanism
  against a versioned Backplane source. Validate both skills, the active
  Superpowers compatibility, `gh` capabilities, and fresh-session discovery
  before reporting success. Do not update upstream as a side effect.
- **Backplane rollback:** Restore the recorded prior Backplane version through
  the host's supported package source or pinned Git revision, then repeat the
  discovery and capability checks. If host replacement happened before a
  failed check, restore and verify the prior version; report if restoration
  cannot be proved. Upstream and issue state remain untouched.
- **Backplane uninstall:** Remove or disable only the Backplane plugin and
  Backplane-owned discovery/configuration. Preserve upstream Superpowers,
  user-authored project files, repository history, and GitHub issues. If a
  shared marketplace is in use, preserve unrelated entries.
- **Superpowers update or removal:** Follow upstream's own supported channel
  and `SUPERPOWERS.md` compatibility process. Backplane may report that its
  dependency is missing or incompatible, but may not silently upgrade,
  downgrade, remove, or replace it.

| Host | Install and update | Rollback and uninstall |
|---|---|---|
| Codex | Add the Backplane Git marketplace, install its root plugin, and refresh the marketplace for a selected new release. | Reinstall from the recorded prior Git ref. Remove or disable only the Backplane plugin; retain a shared marketplace. |
| Claude Code | Add the Backplane marketplace, install its plugin, then refresh the marketplace and update that plugin when its version changes. | Reinstall the prior tagged source and version. Uninstall only the Backplane plugin; retain a shared marketplace. |
| OpenCode V1 | Configure a versioned Git package in `plugin`; change the pinned package spec and restart for an update. | Restore the prior package spec and restart. Remove only the Backplane entry to uninstall. |
| OpenCode V2 | Install a versioned Git package through the plugin manager or `plugins` configuration; update only that package. | Restore the prior package spec and reload. Remove only the Backplane package or configuration entry. |

Each host operation must preserve unrelated plugin entries, record the source
before mutation, and pass a fresh-session discovery check afterward. A host
that cannot pin or restore the previous version cannot claim rollback support
until a tested recovery path is documented.

An incompatible candidate or failed verification leaves the last verified
installation available where the host permits restoration. A dirty checkout,
path collision, unknown provenance, unsupported host API, or unavailable
required `gh` capability fails closed with a specific repair instruction.

## Backlog lifecycle and mutation

Status, orientation, recommendation, and candidate-list requests are read-only.
Selecting an issue causes complete native intake and eligibility checks, but
selection alone never changes a lifecycle label. Explicitly starting,
resuming, designing, preparing, submitting, blocking, or finishing a work item
authorizes the corresponding evidence-gated transition as part of that workflow;
no redundant confirmation is required for an already authorized transition.

An open tracked issue carries exactly one `backplane:*` lifecycle label.
Preserve unrelated labels. Re-read complete issue state and relationships
immediately before each mutation. If `updatedAt` differs from the revision
consumed by the plan, reconcile semantics before proceeding. Zero or multiple
Backplane labels, changed acceptance criteria without current design and plan,
or an unresolved native blocker stop the intended transition until repaired.

| Event with evidence | Result |
|---|---|
| Design or issue refinement actually begins | `backplane:designing` |
| Approved design and current plan; blockers clear | `backplane:ready` |
| Eligible selected leaf begins its first execution task | `backplane:active` |
| Concrete impediment stops work, with reason and resume target recorded | `backplane:blocked` |
| Implementation, required review, and worktree verification support submission | `backplane:review` |
| Integrated delivery meets acceptance and passes fresh verification | Close with reason `completed` |

The full transition graph, blocked-state recovery, and `not planned` closure
rules remain in `skills/managing-superpowers-backlog/references/github-issue-contract.md`.
Apply a label change in one `gh issue edit` call, then re-fetch and verify one
expected Backplane label and unchanged unrelated labels. An open pull request,
prepared worktree, checked plan box, or elapsed deadline is never completion
evidence. Installation and dependency operations never mutate backlog state.

## Verification contract

Follow-up package implementation plans must exercise Codex, Claude Code,
OpenCode V1, and OpenCode V2 as four fresh-session variants. For each,
record host version,
Backplane revision, upstream source and revision, `gh` capability result, and
observed discovery of the three required skills from their separate packages.
Test clean installation, adoption of compatible existing upstream, repeat
installation, update, rollback, uninstall, and failure with dirty or
incompatible existing state. Verify that unrelated user files and the
independently managed upstream installation survive Backplane changes.

Exercise status-only, selection, design, readiness, execution, submission,
blocking, review changes, and verified completion against disposable or
explicitly authorized test issues. Assert zero mutation for read-only and
selection-only paths, exactly one correct Backplane label on each open tracked
issue after a transition, preservation of other labels, and correct closure
reason after verified integration. The existing five named Backplane
conformance checks remain required for upstream compatibility; fresh
four-variant package tests supplement them. No verification step assumes a
project language or uses pytest.

Issue #2 is verified by reviewing this contract against project rules and
current primary host documentation, walking the lifecycle and failure
scenarios, and confirming that the follow-up test matrix is assigned to
implementation leaves. Live installation and mutation checks occur in those
leaves after their package surfaces exist.
