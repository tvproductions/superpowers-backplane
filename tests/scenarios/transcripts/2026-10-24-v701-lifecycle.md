The lifecycle is:

```text
invalid review + active
  → repair to review
  → active for requested implementation changes
  → blocked, recording active as the resume target
  → active after blocker resolution and gate revalidation
```

The release deadline, maintainer pressure, and preparation effort do not replace evidence gates.

Before any proposed mutation, retrieve the complete current issue:

```sh
gh issue view 24 --repo example/widgets --json number,title,body,state,stateReason,issueType,labels,parent,subIssues,subIssuesSummary,blockedBy,blocking,closedByPullRequestsReferences,updatedAt,url
```

Retrieve discussion when needed to establish review requests, authorization, or blocker evidence:

```sh
gh issue view 24 --repo example/widgets --comments
```

For a repository’s first use, also inspect `gh label list --repo example/widgets` and confirm the six lifecycle labels and their meanings. Missing labels require separately authorized creation.

1. **Fail closed on the initial invalid state, then repair it.**

   Two lifecycle labels violate the exactly-one rule. Stop ordinary transitions and execution until the inconsistency is repaired. The submitted implementation and review evidence support `backplane:review`; the accidental `backplane:active` label does not.

   After confirming current evidence, revision, and authorization for the repair:

   ```sh
   gh issue edit 24 --repo example/widgets \
     --remove-label backplane:active \
     --add-label backplane:review
   ```

   Record the repair’s rationale if it is not already represented:

   ```sh
   gh issue comment 24 --repo example/widgets \
     --body "Repaired conflicting lifecycle labels to backplane:review: the implementation was submitted for review; backplane:active was accidental. Requested implementation changes are handled as a separate transition."
   ```

   Re-fetch the complete issue and verify that `backplane:review` is the sole lifecycle label and `security`, together with every other unrelated label, remains unchanged.

2. **Return review to active for requested changes.**

   Review has explicitly requested implementation changes. Re-read the issue and relationships, reconcile any `updatedAt` drift against the approved design and current plan, and confirm the rework is covered and execution can actually begin.

   ```sh
   gh issue edit 24 --repo example/widgets \
     --remove-label backplane:review \
     --add-label backplane:active
   ```

   Re-fetch and verify exactly one lifecycle label, `backplane:active`, with unrelated labels preserved. The issue remains open. A ready-for-merge claim does not establish completion.

3. **Enter blocked when the external condition prevents progress.**

   Identify the concrete blocking condition and the evidence needed to release it. Where another issue is the blocker, use the native blocking relationship rather than replacing it with prose.

   Record the resume target before applying the label transition:

   ```sh
   gh issue comment 24 --repo example/widgets \
     --body "Blocked: <concrete external condition>.
   Resume target: backplane:active
   Release condition: <specific evidence required to establish resolution>."
   ```

   Re-read after this comment, account for its timestamp change, and confirm the expected active state and blocker before transitioning:

   ```sh
   gh issue edit 24 --repo example/widgets \
     --remove-label backplane:active \
     --add-label backplane:blocked
   ```

   Re-fetch and verify `backplane:blocked` is the sole lifecycle label and `security` remains.

4. **Resume active only after revalidation.**

   Read the issue, native relationships, recorded resume target, and resolution evidence again. Verify that the external condition and every other execution blocker are resolved; the issue remains an open executable leaf with a complete contract; approved design and current plan still cover its semantics and requested rework; selection and execution authority remain valid; and execution can resume under project rules.

   Resumption uses the recorded active target; it does not require relabeling through ready.

   ```sh
   gh issue comment 24 --repo example/widgets \
     --body "Blocker resolved: <evidence reference>. Revalidated the recorded backplane:active resume target, current issue semantics, approved design/plan, and execution prerequisites."
   ```

   Re-read and reconcile the comment’s timestamp change before applying:

   ```sh
   gh issue edit 24 --repo example/widgets \
     --remove-label backplane:blocked \
     --add-label backplane:active
   ```

   Re-fetch and verify exactly one lifecycle label, `backplane:active`, and all unrelated labels unchanged.

Each transition removes and adds labels in one `gh issue edit` invocation. These commands avoid replacing the complete label set. They do not provide a revision lock: unexpected concurrent changes require stopping and reconciling.
